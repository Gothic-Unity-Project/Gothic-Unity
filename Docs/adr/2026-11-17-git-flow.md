# ADR: Git flow with develop, release and main

- Date: 2026-11-17
- Technical details: CONTRIBUTING.md > Branching

## Context

Features and fixes landed directly on main, so main was never a version players could rely on. We want main to hold released versions only, while new features keep coming in during a release.

## Decisions

1. **Git flow as written in CONTRIBUTING: `develop` for features, `release/x.y.z` for a release, `fix/*` into a release, `hotfix/*` from main. `develop` is the default branch, `main` only holds releases.** Not chosen: working on main only (trunk-based), because main could not stay a stable release for players while features land. Not chosen: a long-lived branch called `dev`, because `develop` is the standard git flow name.
2. **PRs are merged with merge commits only, no squash and no rebase merges.** Squashing loses meaningful commits and breaks the back-merges release -> main -> develop: tags are no longer reachable from develop and the same conflicts come back again and again. A required linear history has the same problem. To keep a branch current, prefer GitHub's "Update with rebase".
3. **`main` and `develop` are protected by a GitHub ruleset:** no deletion, no force push, a PR with 1 approval, and the branch must be up to date before merging.
4. **A decision record counts as accepted once it is merged into `develop`, a `release/*` branch or `main`, whichever comes first.** It used to be: merged into main.
5. **A GitHub release targets `main`.** It would default to the default branch `develop`.

## Consequences

- Every PR names its base: `develop`, `release/x.y.z` or `main`. Reviews and tools compare against that base.
- Release and hotfix branches must be merged back into `develop`, or their fixes are lost.
- Merge commits make the history busier, but tags and back-merges stay correct.
